```
docs/
├─ 通用/                           ← 与具体项目无关，可整目录拷进任何新项目

│  ├─ 03-AI协作与文档义务.md        单一事实源 / 开工清单模板 / 交接便条模板 / 文档同步矩阵 / AI 铁律
│  └─ 04-排障方法与通用坑.md        六步排障法 / 坑清单模板 / Windows·Node·CI·文件系统·Electron 通用坑 / 验证技法 / 判据表
└─ 项目/                           ← 本项目的专属文书
   ├─ 00-文档导航.md（本文）
   ├─ 01-新会话开工清单.md           ★ 每次开工先读：状态锚点、交接便条、下一步、挂起事项（原 §0）
   ├─ 02-架构与铁律.md               项目铁律、工程地图、代码风格落点、DSH 侧规则、命名落点（原 §1~§3 + 命名约定）
   ├─ 03-坑清单.md                   ★ 59 条编号坑（现象/根因/修法/验证）+ 附录（原 §4，权威）
   ├─ 04-范例与检查点.md             端到端代码范例、检查点命令清单、提交规范（原 §5~§7）
   └─ 计划/                         四份计划与进度文书（事实源，只追加不重写）
      ├─ Electron施工计划与进度.md   ★ 唯一进度事实源：进度快照表 + 恢复协议
      ├─ DeepSeek-Harness桌面应用封装计划书.md   架构拆解与方案选型
      ├─ Electron构建安装包计划书.md             构建流水线、签名、坑清单
      └─ DSH更新按钮计划书.md                    DSH 更新按钮（S1/S2/S3）设计
```

代码侧文书：`desktop-electron/README.md`（怎么跑、怎么排障、发布步骤）。项目级文书：根 `CHANGELOG.md`（按版本倒序，含事故复盘）。

## 2. 我该读哪份？

| 我要做的事 | 读 |
|---|---|
| **新会话开工 / 接手项目** | `项目/01-新会话开工清单.md` → `项目/计划/Electron施工计划与进度.md` 最后一行 |
| 写代码、定命名、定结构 | `通用/01-代码规范.md` + `项目/02-架构与铁律.md` |
| 提交、跑门禁、发版、传 GitHub | `通用/02-提交与门禁.md` + `项目/04-范例与检查点.md` |
| 交接、写文书、和其他 AI 会话协作 | `通用/03-AI协作与文档义务.md` |
| 排障（尤其"别人机器上不行"） | `项目/03-坑清单.md` → `通用/04-排障方法与通用坑.md` → `desktop-electron/README.md` |
| 查历史决策与阶段进展 | `项目/计划/` 四份 + 根 `CHANGELOG.md` |

## 4. 维护义务（新会话必须遵守）

1. **新坑回填到 `项目/03-坑清单.md` 并顺延编号**；若这条坑换个项目也会遇到，**同时**补进 `通用/04-排障方法与通用坑.md`，两处口径必须一致。
2. **通用文书里不写项目专有名词**（DSH、Electron 壳、asar 这些只出现在"实例"位置）。若某条规则只在特定技术栈成立，写进对应小节标题里，不要混进通用条款。
3. **每次改动按 `通用/03-AI协作与文档义务.md` §4 的矩阵同步文书**，同一个 commit 内完成。
4. **进度只写进 `项目/计划/Electron施工计划与进度.md`**（唯一事实源）+ `CHANGELOG.md`，其他地方只引用不复制。
