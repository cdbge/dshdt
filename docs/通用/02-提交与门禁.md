# 通用：提交规范与门禁体系

> **适用范围**：任何有版本控制、任何要交付给别人的项目。
> **核心命题**：**没有门禁的提交等于没有提交**——别人无法判断这次改动是不是好的，未来的你也无法。
> 配套：`01-代码规范.md`（写什么）、`03-AI协作与文档义务.md`（谁改哪份文书）、`04-排障方法与通用坑.md`（错了怎么查）。

---

## 1. 提交信息规范

**格式**：`<类型>(<范围>): <中文动作>（关键数字）`

```
feat(0.4.6): 宿主崩溃可诊断 —— stdio 两级化 + --diag 取证 + 启动前 preflight
fix(0.4.6): 修复插件挂载写坏 profile 补丁层（YAML 双节点）导致宿主启动即 code=1
chore(repo): 开源前清理工作区（释放 1.1 GB；删 14 个一次性探针脚本）
docs(通用): 文书重构为「通用规范 + 项目文档」两层
```

| 类型 | 用途 |
|---|---|
| `feat` | 新能力（用户可感知） |
| `fix` | 修缺陷（写清**现象**） |
| `docs` | 只改文书 |
| `chore` | 仓库维护、依赖、清理、脚本 |
| `refactor` | 不改行为的结构调整 |
| `test` | 只加/改测试与门禁 |
| `build` / `ci` | 构建配置、流水线 |

规则：
1. **标题里要有数字**：断言数、文件数、体积、版本、耗时——数字是"这次到底动了多少"的唯一客观线索。
2. **范围用版本号或模块名**，全仓库通用改动写 `repo`。
3. **正文写「为什么 + 怎么验证的」**，不写「改了哪些文件」（diff 已经说了）。删东西要写**删了什么、为什么安全**（历史可追溯 / 已重建 / 已被 X 取代）。
4. **一事一提交**：清理、重构、功能、文书分开。混在一起的提交在排障时是负资产（无法二分定位）。
5. **不 commit 不进下一阶段**：工作树里躺着上一阶段的半成品，是"两件事互相污染"的开始。

## 2. 门禁体系（分层，越靠下越贵）

| 层 | 内容 | 要求 | 频率 |
|---|---|---|---|
| **L0 语法** | `node --check` / 编译器 / 类型检查 | 秒级 | 每次改动 |
| **L1 纯逻辑自检** | 单测、状态机、解析器、分级器 | **秒级、可脱网**、纯函数优先 | 每次改动 |
| **L2 集成** | 真起进程/真读写文件/真握手 | 分钟级，隔离目录 | 改动相关模块时 |
| **L3 端到端** | 全链路冒烟（真 UI / 真宿主 / 真网络回环） | 分钟级，需要更宽权限 | 任何主路径改动 |
| **L4 产物** | 打包后的安装包/二进制再跑一次冒烟 | 发版前必跑 | 发布前 |

**分层原则**：**便宜的门禁必须多、必须快、必须能脱网**——它们是日常依赖；贵的门禁只在关键节点跑，跑之前先说清预期耗时（例如"换树验证约 8 分钟"）。

**基线**：把每条门禁的断言数写进文书（如"9 套离线自检 = 242 断言、smoke 72/72"）。数字变了要么是好事（加了断言），要么是坏事（门禁被删）——两种都必须有人解释。

### 门禁脚本的硬要求

1. **幂等、可重复、有退出码**：跑两次结果一致；成功 `exit 0`，失败 `exit 非 0`。
2. **能脱网就跑脱网**：不依赖 registry、不依赖外网服务（镜像配置显式化）。
3. **在隔离目录里跑**：测试数据写在专用临时目录（并被 gitignore 覆盖），绝不碰用户真实数据。
4. **输出就是契约**：`PASS`/`FAIL` 前缀行、结尾一行汇总（`ALL PASS` / `N passed, 0 failed`）。
   ⚠️ **断言名不得以 `PASS`/`FAIL` 开头**：把失败原因写成 `FAIL xxx` 时，输出会变成 `  PASS  FAIL xxx`，任何 `grep FAIL` 的流水线都会把全绿读成失败（踩过）。
5. **负样本必须在内**：只有"正确输入通过"的测试不算测试。每条守卫都要有一条"错误输入必须被拒绝"的断言。
6. **门禁自身也要能自证**：临时目录用完即删、失败也要清理；清理失败要报出来（否则下一次跑会因为残留而误判）。

### 检查点协议（恢复/验证的标准动作）

```
① 动手前先跑基线 —— 全绿才说明"环境没坏"，否则你无法区分"我改坏了"和"本来就是坏的"
② 改动
③ 重跑同一组基线 —— 失败 = 未完成，修完再跑，不"口头通过"
④ 同步文书（见 03-文档同步义务）
⑤ commit
```

**沙箱/权限口径要写清楚**：哪些门禁需要更宽权限（起 GUI、命名管道、原生模块），哪些在受限环境也能跑。把这条写进文书能省下一个人的几小时——有人会在受限环境里连跑失败，然后把环境问题误判成代码自杀（真实发生过）。

## 3. 版本与发布纪律

1. **版本号是需求方的决定，不是开发者的顺手动作**。没有明确指令，**不得**改 `VERSION`/`package.json`/`CHANGELOG` 里的版本号，也不得据此命名备份目录与产物。功能照常开发、提交、更新文书即可。
2. **单一事实源**：一个 `VERSION` 文件（或一个字段），所有地方（UI、安装包名、日志、诊断）都从它读，不许多处手写。
3. **CHANGELOG 按版本倒序**：能力 / 修复 / 已知问题各成条；事故类条目写"现象 → 根因 → 修法 → 验证"。
4. **产物不入库**：安装包、二进制、生成物一律 gitignore，分发走 **GitHub Releases**（或等价制品库）。理由有三：仓库 clone 变重、diff 无意义、历史无法回收（Git 会把每个版本永久留在 `.git` 里）。
5. **发版前必跑 L4**（打包产物冒烟），并记录产物**体积 + 哈希前缀 + 是否签名**（未签名要明说"首次运行 SmartScreen 提示属预期"）。
6. **旧版本产物及时清理**：多版本共存是"发错包"的头号原因（实测：同目录留着旧版安装包，内含过期运行时，装上去会把依赖退回旧版）。发新版后删旧包，或在文件名上做到不可能看错。
7. **回滚要有具体动作**：写清"怎么退回去"（备份在哪、命令是什么），而不是"必要时回滚"。

## 4. 公开仓库前的体检清单

上传到公开平台前，**逐条打勾**（顺序即执行顺序）：

1. **密钥与凭据扫描**：`grep` 常见模式（`sk-`、`api_key`、`Bearer`、`PRIVATE KEY`、`password`），并检查**临时诊断目录**（最容易残留明文凭据的导出快照）。
2. **个人/机器信息**：绝对路径（`D:\...`、`/Users/...`）、内网地址、真实姓名以外的隐私信息；文档里的示例路径改成 `D:\repo\...` 形式。
3. **大文件与历史体积**：`git rev-list --objects --all` 列出历史里最大的 blob。**只在工作树删掉是不够的**——历史里的二进制会永久跟着仓库。`.git` 体积应与源码量匹配（健康值：几 MB）。
4. **`.gitignore` 复核**（三个高频陷阱）：
   - **行尾注释不是注释**：`.dsh/   # 说明` 整行会变成一个失配的模式，该忽略的目录会被 `git add -A` 全部提交（踩过）。注释必须独占一行。
   - **`.gitignore` 不追踪已入库文件**：先入库再补规则是无效的，必须 `git rm --cached`。
   - **忽略规则要覆盖"生成物"而非"某个具体路径"**：生成目录换名后规则就失效了。
5. **行尾与二进制属性**：加 `.gitattributes`——库内统一 LF，Windows 脚本（`.ps1`/`.cmd`/`.bat`）检出 CRLF，二进制显式声明 `binary`（禁止行尾转换）。检查现状：`git ls-files --eol`。
6. **许可证**：公开仓库必须有 `LICENSE`（MIT/Apache-2.0 等）。"没有许可证" = 保留所有权利 = 别人不能合法使用，与公开的目的相悖。
7. **README 面向陌生人重写**：一句话是什么 → 截图/效果 → 快速开始（复制即可跑）→ 文档导航 → 已知限制 → 许可。**内部人视角的导航表不算 README**。
8. **公开前的最后一次全树检查**：`git status` 干净、`git ls-files` 里没有意外文件、门禁全绿、`git log` 里没有"临时提交"（如有，用 `rebase`/`filter-repo` 收拾，越早越便宜）。

## 5. 上传到 GitHub（通用步骤）

```bash
# 1) 本地先确认干净
git status --short          # 应为空
git log --oneline | head    # 提交信息是否可公开（含内部代号/姓名/邮箱？）

# 2) 在 GitHub 网页端新建空仓库（不要勾选 README/.gitignore/LICENSE，避免首推冲突）
#    仓库名 / 可见性 / 许可证按需求方指定

# 3) 关联远端并推送
git remote add origin https://github.com/<用户名>/<仓库名>.git
git branch -M main
git push -u origin main

# 4) 若平台要求 token：用 PAT（勾 repo 权限）或 SSH key，不要把 token 写进 remote URL 后提交
```

后续每次发布：

```bash
git tag -a v0.4.6 -m "DSH Desktop 0.4.6"
git push origin v0.4.6      # 或直接在网页端 Releases 上传 exe 产物
```

**发布物与仓库分离**：仓库放源码与文书，Releases 放安装包。若确实要用流水线自动发布，把签名证书放在平台的 Secret 里，**永远不要放进仓库**。
