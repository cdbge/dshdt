# 通用：AI 协作协议与文档义务

> **适用范围**：任何"人会换、会话会断、上下文会丢"的项目——也就是所有活过一个月的项目。
> **核心命题**：**文书是项目的长期记忆**。代码只记录"是什么"，文书才记录"为什么、做到哪、踩过什么"。
> 配套：`01-代码规范.md`、`02-提交与门禁.md`、`04-排障方法与通用坑.md`。

---

## 1. 三类文书与"单一事实源"

| 文书 | 回答的问题 | 更新时机 |
|---|---|---|
| **规范**（本文件所在体系） | 怎么做才对 | 定下新约定 / 踩到新坑时 |
| **进度事实源**（一份，唯一） | 现在做到哪了 | 每个阶段收尾 |
| **变更日志**（CHANGELOG） | 每个版本发生了什么 | 每次发版 / 每次事故收口 |
| **坑清单** | 哪些坑踩过、怎么绕开 | 每个新坑当场回填 |

**单一事实源原则**：
1. 同一个事实只在一处写全，其他地方**引用**它，不要复制。复制出来的第二份一定会在某次改动后变成谎话。
2. **"待确认"不能写成结论**。三种标记必须区分：
   - ✅ **已实证**（有命令输出、有日志、有哈希）
   - ⚠️ **待确认**（推测，写明"依据是什么、还缺什么证据"）
   - ❌ **已推翻**（写明"曾经以为是 X，被什么证据推翻"——**不要删掉**，否则下一个人会把同一个错误推理再走一遍）
3. **不重写历史**：CHANGELOG 与进度表只追加与更正（在原文旁标注更正），不静默改写。历史的价值在于"当时为什么这么想"。

## 2. 新会话开工清单（模板）

每次新会话/新人接手，**照顺序做**，不要跳：

```markdown
1. 读规范（通用 4 份 + 本项目规范）——尤其"铁律"与"坑清单"
2. 读进度事实源的最后一行快照，确认状态锚点没变
3. 环境自检：
   git log --oneline -3          # 工作树是否干净、最后一条是什么
   <查当前版本/当前运行实例的命令>
4. 跑基线门禁（先跑便宜的那几套）——全绿才说明环境没坏
5. 确认本次任务的边界与红线（哪些操作必须先征得同意）
6. 再动手
```

**动手前的三条自问**：
- 这个改动会被"打包态/生产态"调用吗？（会 → 不能放在只给开发用的目录）
- 它可逆吗？（不可逆 → 先写单测 + 先征得同意）
- 它需要同步哪几份文书？（见 §4）

## 3. 交接便条（模板）

阶段收尾时写一段，放在进度事实源顶部：

```markdown
### 交接便条（YYYY-MM-DD 收工 · 次日照此续接）

**一句话现状**：<当前版本 / 当前部署状态 / 是否还有"等重启才生效"的尾巴>

**本轮做完的事**（按发生顺序）：
1. <动作 + 关键数字 + 验证方式>
2. ...

**下一步（按需取用）**：
1. <可执行的下一步，含命令与前置条件>
2. ...

**挂起 / 已由需求方关闭的事项**：
- <事项 + 关闭原因 + "不要再动它">

**红线**：<仍需先征得同意的操作>
```

**"好锚点"的四条标准**（锚点写不好，交接就是假的）：
1. **可验证**：能用一个命令复现出这个数字（版本号、端口、断言数、文件数、哈希前缀）。
2. **带时间**：`2026-09-12 17:29 重打`——不然无法判断"这是不是最新的"。
3. **说清前提**：`在完整权限下`、`脱网环境下`、`隔离 home 下`——同一命令不同前提结论相反。
4. **标明不确定**：`⚠️ 未定论` + 缺什么证据（例：等对方 host.log）。

## 4. 文档同步义务矩阵

**改动类型 → 必须同步的文书**（把这个表改成自己项目的文件路径，然后当硬性要求执行）：

| 改动 | 规范 | 进度事实源 | CHANGELOG | README | 坑清单 |
|---|---|---|---|---|---|
| 新增用户可见能力 | 能力表/用法 | 加行 + 阶段小节 | 新版本条目 | 能力表 | — |
| 修缺陷 | 若涉及约定则改 | 加行 | 条目（写现象/根因/修法/验证） | — | 新坑回填 |
| 改构建/依赖/打包 | 命令清单 | 加行 | 条目 | 常用命令 | 新坑回填 |
| 改目录结构/命名 | 结构表 | — | — | 目录速查 | — |
| 只有文书变更 | — | 加行（说明只改文书） | — | — | — |
| 归档/删除文件 | 引用路径全部更新 | 加行（写清迁移对照） | — | 导航更新 | — |

铁律：**"文档同步"是这次改动的一部分，不是下一步**。同一个 commit 里做完，缺一不可。

## 5. AI 协作铁律

**必须先征得同意才能做的（写进项目文书当硬规矩）**：
1. 产出可分发的产物（打包、发布、上传）。
2. 修改需求方已安装/已部署的实例（热更新、替换文件、改配置）。
3. 推进版本号、打 tag。
4. 删除或覆盖需求方的数据（用户目录、日志、凭据）。
5. 引入新的外部依赖/联网下载（在受限网络下可能直接卡死）。

**工作方式**：
1. **先读规范再动手**：文书里已经写明的结论（尤其是"这个坑我踩过"），不要用推测覆盖它。踩过的坑重复踩，是最贵的浪费。
2. **先取证，再断言**：说"是 X 导致的"之前，必须有能指到 X 的证据（日志行、退出码、复现步骤）。做不到就写"⚠️ 嫌疑，待确认"。
3. **区分"代码缺陷"与"环境不允许"**：在受限环境里失败 ≠ 代码坏了（命名管道被拦、GUI 起不来、权限不足）。先分类，能省几小时。
4. **小步验证**：一次只改一件事，改完立刻跑最便宜的门禁。别攒一大堆改动再一起测。
5. **结论反转要留痕**：如果上一轮的判断被推翻，**在文书里写明"曾被推翻 + 原因"**，而不是把旧结论删掉。
6. **自省入档**：把自己走过的弯路（误判、白耗的轮次）写进坑清单——它对下一个会话的价值高于成功记录。
7. **失败不"口头通过"**：命令没跑完、断言没绿、日志没看，就不算完成。禁止用"应该没问题"结案。
8. **不确定的破坏性操作，默认不做**：宁可多问一句。

## 6. 反模式清单（出现即停手）

- ❌ 把"我觉得"写成"已确认"。
- ❌ 文书里出现两个都声称自己是"唯一事实源"的文件。
- ❌ 进度表只有结论没有数字，交接便条只有形容词（"基本完成"）。
- ❌ 把已经推翻的结论悄悄删掉。
- ❌ 改了代码但"文档下次一起更"（下次就是永远不会）。
- ❌ 在受限环境里反复重试同一个注定失败的命令，而不去分类原因。
- ❌ 用"临时脚本"改用户数据（临时脚本没有单测、没有回滚、没人审）。
- ❌ 一次提交里混入清理 + 重构 + 功能 + 文书（无法二分定位）。
